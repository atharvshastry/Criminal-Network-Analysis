# Data contract: Python pipeline -> backend/frontend

This is what the AI/graph pipeline (Python, three separate envs: NER, RE,
graph) hands off to the JavaScript backend and React frontend. You should
not need to touch Python at all -- just read the two JSON files below.

## Where the data lives

After `python run_pipeline.py` finishes, two files are written to:

```
SIH project/shared_output/graph_export.json
SIH project/shared_output/findings.json
```

These are regenerated (overwritten) every time the pipeline runs. Treat
`shared_output/` as the one stable handoff point -- nothing inside the
NER/, RE/, or "criminal analysis graph/" folders is meant to be read
directly by the backend.

For a real deployment, the Node backend should either:
- read these two files directly off disk (simplest -- e.g. on server
  start, or on each request if you want it always-fresh), or
- watch the folder (`fs.watch`) and push updates to connected clients
  when the pipeline re-runs.

## graph_export.json

```jsonc
{
  "nodes": [
    {
      "id": "ent_00007",                 // stable canonical entity id -- use this to join/link, never canonical_name (not unique)
      "entity_type": "PERSON",           // one of the ENTITY_TYPES in graph/config.py (19 possible values)
      "canonical_name": "Neeraj Patel",  // display name
      "aliases": ["N. Patel"],           // other surface forms merged into this entity
      "degree": 1,                       // number of direct relationships
      "weighted_degree": 0.5989,         // degree weighted by relationship confidence
      "pagerank": 0.9612,                // 0..1, overall influence/reach
      "betweenness": 0.0,                // how often this entity sits on shortest paths between others ("broker" signal)
      "eigenvector": 0.3536,             // influence via well-connected neighbors
      "community_id": 6,                 // Leiden-detected cluster id -- NOT stable across pipeline re-runs, only meaningful within one export
      "bridge_score": 0.0,               // 0..1, fraction of this entity's edges that cross community boundaries
      "anomaly_flag": -1,                // -1 = flagged anomalous by Isolation Forest, 1 = normal
      "anomaly_score": -0.0279,          // lower = more anomalous
      "source_document_id": "fake_fir.txt",
      "source_type": "FIR"               // FIR | CDR | FINANCIAL | SURVEILLANCE | SOCIAL_MEDIA | CRIMINAL_HISTORY
    }
    // ...
  ],
  "edges": [
    {
      "source": "ent_00007",             // node id
      "target": "ent_00002",             // node id
      "relation_type": "contact_number", // one of RELATION_TYPES in graph/config.py (17 possible values)
      "confidence": 0.5989,              // 0..1, relation-extraction model confidence
      "evidence_text": "The complainant stated that he contacted his colleague Neeraj Patel using 9123456789 after the incident.",
      "source_document_id": "fake_fir.txt",
      "timestamp": null,                 // ISO 8601 string or null -- event time, NOT extraction time
      "amount": null,                    // numeric or null -- set on money-related relations (e.g. involves_amount)
      "kind": "confirmed"                // "confirmed" (real extracted relationship) | "predicted" (AI-suggested hidden link -- see below)
    }
    // ...
  ]
}
```

**`kind: "predicted"` edges are leads, not evidence.** They come from
Node2Vec similarity + shared-neighbor analysis (link_prediction.py) and
are explicitly unconfirmed. The frontend must render them visually
distinct from confirmed edges (e.g. dashed line, different color,
"unconfirmed" badge) -- never present them as established facts. A
predicted edge additionally carries `confidence` as an embedding
similarity score (0..1), not an extraction-model confidence.

## findings.json

```jsonc
{
  "entity_findings": [
    {
      "entity_id": "ent_00007",
      "canonical_name": "Neeraj Patel",
      "finding_type": "key_influencer",   // key_influencer | hidden_broker | community_bridge | odd_hour_activity | activity_burst | general_anomaly
      "severity": "info",                 // info | low | medium | high
      "summary": "Neeraj Patel ranks among the most influential entities in the network (PageRank 0.961), based on both the number and importance of their connections.",
      "evidence": { "pagerank": 0.9612, "eigenvector": 0.3536 }  // shape varies by finding_type -- always traceable back to the number(s) that triggered it
    }
  ],
  "connection_findings": [ /* same idea, for pairs of entities -- currently only populated once predicted links exist */ ],
  "summary_counts": { "total_entity_findings": 8, "total_connection_findings": 0 }
}
```

Every finding is plain-language text ALREADY generated by the Python
side (see `criminal analysis graph/generate_findings.py` /
`config.FINDING_THRESHOLDS` if you ever need to see how a number became
a sentence) -- the frontend just needs to render `summary`, group/filter
by `finding_type` and `severity`, and let a user click through to
`entity_id` in the graph view.

## Suggested minimal backend surface

You (or your JS teammate) decide the actual framework/routes, but the
natural shape is:

- `GET /api/graph` -> the parsed contents of `graph_export.json`
- `GET /api/findings` -> the parsed contents of `findings.json`
- `GET /api/entity/:id` -> a single node + its edges (derivable from
  `graph_export.json` server-side, or query Neo4j directly if the
  backend has its own driver -- either is fine, `shared_output/` doesn't
  require a database round trip)

Nothing above requires the backend to run any Python or reach Neo4j
directly; `shared_output/*.json` is a complete, self-contained snapshot.
If you want the frontend to feel "live", re-run
`python run_pipeline.py` (or its later stages) whenever new source
documents are added, and have the backend pick up the refreshed files.
